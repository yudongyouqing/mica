# CI 时序测试修正（#108）

基线：`dev` / `53efa19`。只调整测试等待条件、测试预算和诊断，不改变生产 IPC 期限、管道并发模型或窗口生命周期。

## 已核对证据

- dev 的 run `42026216193`：100 并发测试只服务了 99 个客户端。
- 搜索修复分支的 run `42746381847` 最新 attempt：同一测试只服务了 93 个客户端。
- 绘制调度分支的 run `42747157223`：两个配置广播测试读到的标题仍为 `powershell`。
- 上述记录支持既有 CI 基线不稳定；失败点漂移本身不能证明所有失败都只有 runner 慢速这一个原因。

## 修正

1. 100 个客户端仍同时竞争一条真实管道，逐一校验请求 id 和 `Applied`。共享截止时间为 `20s + 100 × 250ms = 45s`，包含排队时间；连接成功后的响应等待收紧至最多 5s，并受共享截止时间限制。任何超时、写入失败或错误响应都令测试失败，不降并发、不容忍部分成功、不重试整项测试。
2. 配置测试原先只等待 IPC 可用和窗口可见，但这两者都可能早于 timer 7 的延迟初始化完成。配置 watcher 在延迟初始化末尾才建立：提前写配置会丢失监听事件，提前关闭主窗也可能取消尚未执行的初始化。测试现在启用已有 `MICA_DEBUG_TIMING` 日志，等待延迟段结束后再进行关闭和配置写入；等待上限 30s，并检查进程是否提前退出。配置应用期限调整为 15s。
3. 独立保存被测进程 stderr；禁止自动化崩溃弹出模态框。Windows CI 失败时上传隔离实例的 stderr，保留 7 天，不上传 minidump。生产端 `REPLY_DEADLINE=3s`、`READ_DEADLINE=5s` 和 `WRITE_GRACE=2s` 均未更改。

## 本地验证

- IPC 与 window_lifecycle 共 18 项集成测试通过。
- 完整 workspace 测试通过（287 项通过，4 项忽略），fmt 与严格 workspace Clippy 通过。
- 可控排队实验：仅在测试客户端读完应答后、关闭句柄前临时插入 250ms 休眠，模拟延迟释放唯一管道；实验不改生产代码。
  - 旧 20s 共享预算：20.33s 结束，25 个连接超时，测试按预期失败。
  - 新 45s 共享预算：26.98s 完成，100/100 成功。
  - 实验结束已恢复测试文件，提交中不包含这段休眠。
- 实验原始日志保留在本机临时目录 `mica-ci-budget-probe-57_2wuga` 下的 `old_20s.log` 与 `load_45s.log`。该实验只验证串行排队预算，不代表真实应用性能测量。

## 边界

- 初始化日志表示延迟初始化返回，不单独证明 watcher 成功建立；后续真实文件变更与窗口标题断言继续验证 watcher、广播及配置应用。
- 排队实验不能定位历史广播失败的唯一原因；增加初始化屏障消除了一条明确的测试前置条件竞态。
- 本地通过不等同共享 runner 已稳定，远端 CI 仍须验证；后续若失败，应根据保留的阶段、请求 id 和进程日志继续定位，不能继续盲目增大期限。
- WSL 枚举仍可能阻塞延迟初始化，属于 #107 的生产问题，本修正不会将其标记为已解决。
- 主窗在 timer 7 执行前关闭时，存活副窗可能永久缺失 watcher：这是独立生产缺口，已单列 #109。本轮屏障只验证已建立 watcher 的存活，不覆盖或修复该早关闭场景。
