# 给 GLM 的执行指令

请审阅并逐项执行同目录的 `2026-11-01-comprehensive-hardening.md`，它基于 Mica 本地 `dev` commit `c6ec62b` 的源码检查和 Windows 实测。

你的目标是完善正确性、长期稳定性、性能、内存和交付质量。先解决明确缺陷，再优化资源，最后补体验。不要一次重写项目，不要用增加功能掩盖基础问题。

开始先做以下动作：

1. 读根目录 `CLAUDE.md` 和完整计划，检查当前分支、工作区、commit 是否已变化；对每个发现重新核对，已修复的标明证据。
2. 保留用户未提交修改；按仓库规范从 `dev` 建任务分支。未获授权不合并、不打 tag、不发布。
3. 运行 fmt、Clippy、workspace test，记录基线。注意当前默认测试忽略了性能项。
4. 首轮只做 T01 最小观测和 T02 安全清理。T02 修复前禁止实际运行全局 orphan 清理，包括所谓 dry-run：当前 false 分支仍会杀子进程。
5. 随后推进 T03/T04 生命周期、T05 分屏图集和 T06 IPC。每项先有修前失败的回归，再实现和验证，独立提交。

审查已经发现的高优先级问题：

- 关标签/分屏会 `mem::forget` 整份状态；重启会遗忘 PTY，长期运行资源不可回收。
- 每 pane 独立图集，但所有 pane 的实例仅绑定焦点 pane 图集绘制。
- IPC 先通知再入队；服务端无真实 ACK，客户端仍阻塞读，读写和累积帧缺乏完整预算。
- 关闭最后标签、caption 和实际窗口销毁不统一，窗口计数存在不归零路径。
- OSC7 跨块丢事件，中文 cwd 乱码；OSC133 标记行号依赖 feed 分块；2026 最后事件顺序丢失。
- PTY 两级积压无界、图集持续加页、shaping 完整文本缓存无界；图片限制发生在解码之后。
- 每次 atlas 上传新建整张纹理；持续输出会重置绘制定时器，QT 调度又不同。
- WSL“3秒超时”只有注释没有实现；按空白拆命令串不支持空格路径。
- 搜索拿 UTF-8 字节偏移画格子，并在 UI 同步全量扫回看。

本次基线：

- 默认测试 190 通过、4 忽略，fmt/Clippy 通过。
- 渲染微基准单次 17,243,081 cells/s、67us，仅是本机微基准。
- sidecar release 预算先后 7.8%、10.4%、4.9%、15.8%；3 次失败、1 次通过，未稳定满足 5% 目标。
- 尚未量测完整应用内存、功耗、输入到屏幕延迟和 8h soak；必须建立数据，不能声称已有达标结果。

实施要求：

- 保持三 crate 边界与现有渲染/输入契约；详细保护清单见完整计划。
- 每个 buffer/cache/queue 同时考虑单 pane、单窗口和全进程总预算；给出背压、取消、超限行为，不能直接丢终端字节。
- 修复 `mem::forget` 前调查原有驱动卡死的最小对象，分离可安全释放的 CPU 状态，不把 UI 改成阻塞 drop/join。
- 验证内存至少看 Private Bytes、Working Set、GPU memory、handles、threads；把用户 shell 子进程单独统计。
- 性能报告含受控配置、原始样本、median/p95/p99和修前修后；不要只报最好值和理论收益。
- 先本地查锁定版本 API，必要时查该版本官方文档；不盲目升级依赖，不复制上游实现，不引入 GPL。
- 完整 UIA provider、活进程 tear-off、kitty graphics、per-pixel 透明和默认终端接管属于独立设计项；不得擅自恢复已知故障路径。
- winget 目前按用户决定暂缓；不自动投递、不购买签名、不发布版本。
- 未完成或未测试的地方明确标出；不要因为旧文档写“完成”就跳过生产路径测试。

每轮输出：任务编号、修前复现、修改文件、验证命令/结果、性能与内存数据、风险和未测项、commit，以及下一个任务。完整验收条件以主计划为准。
